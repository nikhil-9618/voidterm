> A 24/7 multi-provider AI terminal for developers and security researchers.
> Not a chat bubble clone — a dense, keyboard-first workspace with a provider fallback mesh.

**One terminal. Every frontier model.** OpenRouter, OpenAI, Gemini, Groq, DeepSeek, and optional
local Ollama behind a single keyboard-native interface. Email-OTP authentication, account-scoped
history, and deep research-grade answers for credentialed users. No daily message limits.

## Features

- **Three-pane terminal workspace** — 280px session sidebar · streaming chat · 320px context
  panel (model matrix, usage, cost, system prompt). Sharp full-width message blocks with a
  2px role accent bar; cyan user, amber assistant, grey system.
- **Provider fallback mesh** — a turn starts on your chosen model. If the provider fails
  *before the first token*, it retries OpenRouter → Gemini → Groq → DeepSeek → OpenAI (primary
  deduped).
  After a token is emitted, an error surfaces instead of splicing two completions.
- **Six providers** — OpenRouter Free Models Router / Gemma 4 31B (default; no card), Gemini 3.8
  Flash / 3.5 Flash-Lite (optional; project must be free-tier eligible), OpenAI GPT-4o/4o-mini,
  Groq Llama 3.3/3.1, DeepSeek V3 / R1 (reasoning traces suppressed), and local Ollama
  (llama3.3, qwen2.5, mistral).
- **Intent policy gate** — a cached Groq classifier routes turns into informational, research,
  defensive, high_risk, or disallowed. Research requires tier ≥ 2; targeted harm is refused
  with a short redirect. See [Intent policy](#intent-policy-and-why-it-exists).
- **Email OTP only** — six-digit codes, bcrypt-hashed, single-use, 10-minute expiry,
  5-attempt cap, rate-limited per email and IP. JWT + database-backed sessions (30 days),
  revocable per device. No password database.
- **Streaming SSE** — per-token events, a blinking `▋` cursor, abort/stop, partial saves on
  disconnect, and provider-reported usage when available.
- **Command palette first** — `⌘K` fuzzy search across actions and sessions. Model selection is
  a keyboard-navigable matrix, not a dropdown. Scanline texture is toggleable.
- **Dense by design** — JetBrains Mono for UI/code, Inter for prose, Fraunces for headings.
  Dark by default (`#0A0E14` / `#E6EDF3` / `#00E5FF`), light mode available.
- **Production plumbing** — zod validation on every route, ownership-scoped queries, origin
  checks on mutations, audit log for auth and privileged access, markdown sanitized by
  `react-markdown` (no raw HTML), syntax-highlighted code with line numbers and per-line copy.

### Stack

Next.js 14 (App Router) · TypeScript strict · Tailwind CSS · shadcn/ui primitives (Radix) ·
Prisma + PostgreSQL · `jose` JWT · `bcryptjs` · Resend · Upstash Redis + Ratelimit ·
OpenAI SDK + OpenRouter + Gemini REST SSE + Ollama NDJSON · zod · lucide-react · react-markdown/GFM ·
react-syntax-highlighter.

## Quickstart

**Requirements:** Node.js ≥ 18.17 (20 LTS recommended), PostgreSQL 14+, npm.

```bash
git clone <your-repo-url> voidterm
cd voidterm
cp .env.example .env

# Generate a real JWT secret (min 32 chars)
openssl rand -base64 48     # paste into JWT_SECRET

npm install                 # installs deps; Prisma client is generated by dev/build
```

Start PostgreSQL. Either use a hosted database (Neon/Supabase) or the provided compose file:

```bash
docker compose up -d postgres
# DATABASE_URL="postgresql://postgres:postgres@localhost:5432/voidterm?schema=public"
```

Create the schema and boot:

```bash
npx prisma db push
npm run dev
```

Open **http://localhost:3000**. Enter an email on `/login`. With `RESEND_API_KEY` unset
in development, the code is printed to the server console:

```
[DEV OTP] email=you@example.com code=123456
```

No AI provider keys? The UI, auth, history, and policy gate all work. Chat stays disabled until
at least one provider key is set. The default no-card path is an OpenRouter API key using its
free models; Gemini remains available when its project has free-tier access.

### Resend domain verification (SPF, DKIM, DMARC)

Resend will only send from a domain you have verified. Until then, `onboarding@resend.dev`
only delivers to the account owner's address.

1. In Resend → **Domains → Add Domain**, enter a subdomain you control, e.g.
   `mail.yourdomain.com`.
2. Add the exact DNS records Resend shows at your DNS provider:
   - **MX** record for the sending subdomain (Resend's inbound/bounce routing).
   - **TXT SPF** record — typically `v=spf1 include:amazonses.com ~all` on the sending
     subdomain. Use the exact value from Resend; do not create a second SPF record for the
     same host.
   - **TXT DKIM** record(s) — one or more `resend._domainkey...` records with the public key
     Resend generates. These sign your mail.
3. Add a DMARC record at `_dmarc.yourdomain.com` (start permissive, then tighten):

   ```
   v=DMARC1; p=none; rua=mailto:dmarc@yourdomain.com; adkim=r; aspf=r
   ```

   Move to `p=quarantine` once you have confirmed legitimate mail authenticates. DMARC aligns
   SPF/DKIM with your From domain; without it, large receivers may treat OTP mail as suspect.
4. Wait for Resend to show **Verified**, then set:

   ```
   EMAIL_FROM="VOIDTERM <login@mail.yourdomain.com>"
   ```

5. Send yourself a real login code and confirm SPF/DKIM pass (Resend's dashboard and the
   message headers show authentication results).

### Auth flow

1. `POST /api/auth/send-otp` — generate `crypto.randomInt(0, 1_000_000)`, bcrypt-hash (cost 10),
   delete previous unused codes for the email, store with 10-minute expiry, rate limit
   (5/email/hour + 20/IP/hour via Upstash), send with Resend. Always returns
   *“If that email is registered, a code was sent.”*
2. `/verify` — six auto-advancing boxes with paste/OTP-autofill support.
3. `POST /api/auth/verify-otp` — find most recent unused/unexpired code, reject at 5 attempts,
   `bcrypt.compare`, consume atomically, upsert user, create a Session row (SHA-256 of an
   independent random token, 30-day expiry), sign a 30-day HS256 JWT
   `{sub, sid, email, tier}`, set `session` as `HttpOnly; Secure (prod); SameSite=Lax; Path=/`.
4. `GET /api/auth/me`, `POST /api/auth/logout`, `GET|DELETE /api/auth/sessions`,
   `POST /api/auth/logout-all`.

The JWT is never trusted alone: `getSessionFromCookies()` verifies signature/claims **and**
loads the Session row, checks the user binding and expiry. Deleting the row revokes the token
immediately. RLS is enforced at the API layer — every conversation/message query includes
`userId` in the `where` clause; IDs from the client are never used without an ownership check.

### Chat flow

`POST /api/chat` requires a session, validates `{conversationId?, message 1..32000, model,
systemPrompt?, regenerate?, attachments?}` with zod, applies a 100/hour per-user limiter,
classifies intent, applies policy, verifies/creates the conversation, saves the user turn,
builds the last 30 messages as history, and returns
`text/event-stream` (`no-cache`, `keep-alive`, `X-Accel-Buffering: no`):

```
data: {"type":"token","token":"..."}
data: {"type":"done","conversationId":"...","messageId":"...","providerUsed":"groq","usage":{...}}
data: {"type":"error","error":"..."}
```

On `done` the assistant message is saved, `updatedAt`/model/systemPrompt are updated, and the
client replaces `/c/new` with `/c/[id]`. On disconnect the upstream stream is aborted and any
partial assistant text is saved. `runtime='nodejs'`, `maxDuration=60`.

### Intent policy and why it exists

The classifier (Groq `llama-3.1-8b-instant`, strict JSON, 1-hour Redis cache keyed by
SHA-256 of the message) sorts each turn:

| Intent | Tier < 2 | Tier ≥ 2 | Response modifier |
| --- | --- | --- | --- |
| `informational` | allowed | allowed | — |
| `research` (CVE, malware analysis, RE, pentest concepts, CTF) | `403 login_required` | allowed | — |
| `defensive` (detection, hardening, IR) | allowed | allowed | “Emphasize detection and mitigation.” |
| `high_risk` (technical detail + a specific real person/system/account target) | `403 login_required` | `400 refused` | Short refusal + adjacent legitimate capability |
| `disallowed` (ready-to-use phishing kit against a real service, credential stealer, keylogger, CSAM, bioweapons, mass-casualty) | `400 refused` | `400 refused` | Brief refusal + redirect |

**Why this exists (operator liability, not moral theatre).** Hosting a general-purpose model
is defensible; producing a **weaponized artifact** or **targeted assistance against a specific
real person or system** is where operators incur real legal and platform risk. Breadth of
technical detail is not the risk — malware analysis, exploit development concepts, and
detection engineering are legitimate research and defensive work. So the product is
*permissive for depth* and restrictive only at the point of concrete harm: a named target or a
ready-to-use harmful artifact. Refusals are short and offer the adjacent defensive capability
instead of lecturing. Tier-gating research-grade material means there is an accountable,
authenticated party behind it, and every login, policy block, and tier-3 access is written to
`AuditLog`.

**Failure mode:** if Groq is unreachable or unconfigured, the classifier fails open to
`informational`. This keeps the product available; auth, rate limits, provider safeguards, and
auditing still apply. Operators who require strict routing must configure `GROQ_API_KEY`.
This table is a product policy, not legal advice — review it with counsel for your jurisdiction.

## Deploying to Vercel

1. Push the repo to GitHub and import it in Vercel.
2. Create a production PostgreSQL database (Neon/Supabase) and run the schema push **once**
   from your machine with the production URL:
   ```bash
   DATABASE_URL="postgresql://...?sslmode=require" npx prisma db push
   ```
   Add the same URL to Vercel → Settings → Environment Variables.
3. Add every required env var (`JWT_SECRET`, `EMAIL_FROM`, `RESEND_API_KEY`, provider keys,
   Upstash). Generate the JWT secret with `openssl rand -base64 48`; never reuse the dev one.
4. Build command: `npm run build` (already runs `prisma generate`). Install command: `npm ci`.
5. Streaming routes need the Node runtime (already exported) and a plan whose function timeout
   supports 60s. On plans capped at 10s, long answers may cut off — use a container/Node host
   or shorten `maxDuration`.
6. Verify production: `/login` renders, a real OTP email arrives, a chat turn streams, provider
   fallback is exercised by temporarily using an invalid primary key, and `/api/auth/sessions`
   shows the deployed session.
7. **Ollama and `public/uploads` do not work on Vercel.** Use hosted providers and Supabase
   Storage (make the bucket public, or adapt the upload route to signed URLs).8. If you use Upstash, rate limits and the intent cache are shared across instances. Without it, production uses the shared Postgres fixed-window limiter; development uses an in-process limiter. If the database limiter itself fails, the app temporarily falls back to per-instance memory.

### Docker (local services)

docker compose up -d postgres   # Postgres 16 on :5432

The app's rate limiter uses Upstash's HTTP API when configured; the local Redis container is

## Security notes

- OTP codes are bcrypt-hashed, single-use, expire in 10 minutes, capped at 5 attempts, and
  invalidated when a new code is issued. The send endpoint never reveals account existence.
- Session cookies are `HttpOnly`, `Secure` in production, `SameSite=Lax`, `Path=/`, 30 days.
  The JWT is verified **and** the Session row is checked; revocation is immediate.
- Every conversation/message/attachment read and write is scoped by the authenticated
  `userId`; missing resources return 404 rather than leaking existence.
- Mutating routes validate the request `Origin` against the host (CSRF defence in depth),
  and all bodies are zod-validated with explicit bounds.
- Markdown is rendered without `rehype-raw`; raw HTML is not interpreted. Code is displayed
  through a syntax highlighter, not executed.
- Auth events, policy blocks, tier-3 access, uploads, and conversation deletion are audited.
  Production never logs OTPs or secrets; the dev OTP console log only exists when
  `RESEND_API_KEY` is unset in development.
- CSP, HSTS, frame denial, nosniff, Permissions-Policy, COOP, and CORP headers are set globally.
- Uploads are checked by magic bytes, restricted to an allowlist, and stored under canonical
  server-generated names/MIME types; SVG, HTML, and executable formats are rejected.

## Known limitations / next steps

- The intent classifier depends on Groq; without it, classification fails open.
- Rate limiting uses Upstash when configured; production otherwise uses a shared Postgres fixed window. It falls back to per-process memory only if the database limiter itself fails.
- Next.js 14.2.35 still has published advisories that require the breaking Next.js 16.4.5 upgrade.
- CSP currently permits inline scripts because Next 14 injects them; move to a nonce policy with the major upgrade.
- Attachments require a **public** Supabase bucket with the current URL scheme; switch to
  signed URLs for private storage.
- Client-disconnect partial saves are best-effort: a hard platform kill can lose the tail of a
  response, but every completed `done` event is persisted before the event is sent.
- `deepseek-reasoner` reasoning tokens are intentionally not surfaced in the UI.
- The code block “run” button is a deliberate placeholder; no sandbox runtime is bundled.
